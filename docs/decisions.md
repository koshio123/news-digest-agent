# 設計判断

何を選び、何を諦めたかを記録する。新しい判断は末尾に追記する。

## 1. 「前回実行から」の期間と既読の扱い

- 期間の開始は「前回の**成功した**実行の終了時刻」。失敗した実行は failed として記録し、次回はその前の成功から取り直す（取りこぼさない）。
- ただし取得は開始時刻より少し前から行う（`overlap_days`。arXiv 3日、RSS・Web 1日）。arXiv は投稿から公開まで1〜2日遅れるため、期間ぴったりで取ると「前回実行後に公開されたが、投稿日時は前回より前」の論文を永久に取りこぼす。
- 重なった分は既読DB（`items` テーブル）で除くので、「前回の実行に含まれたものは除く」は守られる。
- 既読にするのは**新着として処理したすべての記事**（事前フィルタで落ちたもの・採点で低かったものも含む）。掲載したものだけを既読にすると、毎回同じ低スコア記事を再採点することになり、コストが増えるだけで結果は変わらないため。
- `--dry-run` は既読にもせず実行も記録しない（プロファイル調整用）。

## 2. 事前フィルタはキーワード、本採点はLLM

- 全件をLLMで採点するとコストがかさむので、キーワード一致で足切りしてからLLMに渡す（上限 `max_candidates`）。
- 英語のキーワードは単語境界で照合する（"EV" が "Neuron" や "review" に一致しないように）。日本語は部分一致。
- 検索系ソース（arXiv・Tavily）はクエリが興味から作られているので底上げする。RSSはキーワードに1つも一致しなければ落とす。
- 埋め込みによる意味的なフィルタはフェーズ3で評価セットを作ってから比較する。

## 3. 採点は3軸の整数＋コードで総合点

- LLMには関連度・応用性・インパクトを1〜5の整数で付けさせ、総合点（0〜100）は重みを使ってコードで計算する。LLMに総合点を直接出させると、重みの変更が反映されず、採点のぶれも追えないため。
- 採点は15件ずつまとめて1回のLLM呼び出しにし、Send で並列実行する。記事IDは8文字の短縮IDで渡し、トークンを節約する。

## 4. グラフの並列化は Send API

- 取得は「arXiv 1タスク＋RSSフィードごと＋Web検索クエリごと」に Send で分岐する。arXiv は利用規約（3秒間隔）があるので1タスク内で逐次実行する。
- 並列ノードが書き込むキー（`raw_items`, `scored`, `summaries`, `errors`）には `operator.add` の reducer を付ける。
- 1つのソースやバッチの失敗で全体を止めない。失敗は `errors` に積み、ダイジェストの末尾に表示する。

## 5. フィードバックは Slack のリアクションで集める

- ボタン（Interactive Components）は公開エンドポイントが必要になるため、MVP では使わない。
- 代わりに記事ごとにメッセージを分けて投稿し、次回実行の最初（`collect_feedback`）で直近7日の投稿の 👍/👎 を `reactions.get` で読む。サーバー不要で、自分専用の運用に合う。
- CLI（`digest feedback <ID> up|down --note ...`）でも付けられる。メモは採点プロンプトに「理由」として渡る。
- 反映方法は、最近のフィードバック20件を採点プロンプトに「好みの傾向」として入れる方式。プロファイルの自動更新はフェーズ5。

## 6. LLM は "provider:model" で切り替える

- `init_chat_model` を使い、`.env` の `LLM_FAST` / `LLM_STANDARD` で Anthropic API とローカルの Ollama を切り替える。
- 定期実行は無人で毎日回るので、サブスクリプションのログインを使う方式（Claude Code 経由）は使わない。API課金かローカルLLMにする。

## 7. 依存はクロージャで注入する

- ノードは `build_graph(deps)` 内のクロージャとして定義し、LLM・HTTP・DB・通知先を `Deps` で受け取る。テストでは偽LLMと `httpx.MockTransport` に差し替え、実APIを呼ばずにグラフ全体を検証する。
- LangGraph の checkpointer は使わない。1回の実行は数分で終わり、途中再開より「失敗したら次回まとめて取り直す」方が単純なため。

## 8. 採点の失敗は「既読にしない」

- 採点がすべて失敗した場合（LLMの認証エラー・障害）は実行を失敗させる。成功扱いにすると未採点の記事が既読になり、二度と出てこないため。期間も進まないので、次回に取り直す。
- 一部のバッチだけ失敗した場合は実行を続け、採点されなかった記事だけ既読にしない。
- `ANTHROPIC_API_KEY` は SDK が環境変数から直接読むので、起動時に `.env` を環境変数へ読み込む（既存の環境変数は上書きしない）。

## 9. Anthropic モデルには temperature を渡さない

- 新しい Claude モデルは `temperature` を指定すると `400: temperature is deprecated for this model` になる。`make_chat_model` は Anthropic のときだけ指定を省き、Ollama などローカルLLMには従来どおり `temperature=0` を渡す。

## 10. 状態は Pydantic モデル、Studio 用のグラフはファクトリ

- 状態（`DigestState`）と Send の引数（`FetchTask` など）は Pydantic モデルにする。Studio で状態を編集してフォークすると、値は JSON（dict・文字列）でチェックポイントに入る。TypedDict のままだとノードに dict が届いて落ちる。Pydantic なら LangGraph がノードに渡す前に検証して `Item` や `datetime` に戻す。
- LangGraph は将来、チェックポイントから未登録のクラスを復元するのを止める（`LANGGRAPH_STRICT_MSGPACK`）。`langgraph dev` のサーバーには許可リストを渡す設定が無い。ただし復元できなかった値は dict で戻り、上の検証で型に戻るので、厳格モードでも動く（検証済み）。
- `langgraph.json` はグラフそのものではなくファクトリ（`studio.make_graph`）を指す。サーバーが実行ごとに呼ぶので、`profile.yaml` の変更が再起動なしで反映される（`langgraph dev` の自動リロードは `.py` しか見ない）。ファクトリはイベントループ上で呼ばれ、ブロッキングI/Oはエラーになるので、ファイル・DBを開く処理は `asyncio.to_thread` で行う。
